# toolname

工具名 → 程序内可用的标识符：一条**单一真相**（规范名判定 `IsJSIdent` + 规整 `Normalize`）—— oagentkit 模块矩阵 **tier 0**（基础层：纯标准库、零第三方依赖、零重量级地板）。

```bash
go get github.com/oagentkit/toolname
```

| 包 | 职责 |
|---|---|
| `toolname` | 工具名净化原语：规范名/JS 标识符净化/一致性校验 |

## 定位

**tier 0** — 基础层：纯标准库、零第三方依赖、零重量级地板，可被零依赖核心安全依赖。

## 它解决什么

工具名要在两处被规整成同一个字符串：

- **生产侧**（goagent-kernel 的 `tooldisclose`）：从工具目录派生给模型看的调用形态——形态里的函数名必须是**净化后**的名字，因为程序里真正挂上去的就是净化后的那个（kernel 的 `ptc` 把绑定挂在 `host.<净化名>` 上）。
- **消费侧**（goagent-kernel 的 `ptc`）：把绑定挂到 host 对象上，并校验形态串里的函数名等于净化后的绑定名。

两侧必须**逐字一致**，否则就是「生产侧派得出、消费侧认不出」的夹缝：生产侧返回 `get-logs(h)`，消费侧要的是 `get_logs(h)`，形态在装配期被拒——而症状是「工具明明在目录里，程序就是调不通」，排查时极容易先怀疑模型或宿主。

这条规则**曾经**在两个包里各写一份（规范名写成两份、净化规则又各写一份），于是两侧对「工具名长什么样」的假设漂移开：生产侧照抄目录里的原名，消费侧按净化后的名字挂载，契约在文档里写着「直接可用」，代码里却拒。

抄一份规则省一个包，但那份规则有边界（数字开头补前缀、前导非法字符跳过、撞名即拒），任何一边改了而另一边没改，契约就静默断掉——而断掉的形态是「文档说好的，程序就是跑不通」。

## 规整规则

| 输入 | 结果 | 说明 |
|---|---|---|
| `get_logs` | `get_logs` | 合法 JS 标识符，原样保留 |
| `9lives` | `_9lives` | 数字开头 → 前置 `_` |
| `-x-` | `x_` | 前导非法字符**跳过**（不记 `_`）；已开始后的非法字符记 `_` |
| `get-logs` | `get_logs` | `-` 记为 `_` |
| `!!!` | （空串） | 全部非法 → **无法**规整；调用方必须当「这个名字用不了」处理 |

「前导非法字符跳过而不是记 `_`」是刻意的：`-x-` 规整成 `x_` 而不是 `_x_`，前者读起来像名字，后者像内部产物。

`Normalize` **不保证唯一**：`get-logs` 与 `get_logs` 都得到 `get_logs`。撞名是否允许由调用方决定——本包只提供规则，不做集合级判定。

## API

- `IsJSIdent(s string) bool` —— s 能否**直接**作为 JS 标识符使用（只问「原样用行不行」）
- `Normalize(name string) string` —— 不行的话该用哪个（问「不行的话用什么」）

两者必须用同一套字符规则，否则会出现「这里说行、那里规整成另一个」的夹缝。

## 迁移

本包自 `github.com/oekit/pkg/toolname` 归位而来（那处 v0.58.2 标记 Deprecated、v0.59.0 删除）。**API 逐字一致**，迁移只改 import 路径：

```go
// 旧
import "github.com/oekit/pkg/toolname"
// 新
import "github.com/oagentkit/toolname"
```

为什么归位：它的概念域是**工具治理**（与 toolgate / guardx 同族），不是通用基础设施——留在基线层会让基线层开始「认识工具」。

## 边界

- **零第三方依赖**（go.mod 无 require，仅标准库）
- 不做集合级判定（撞名、重名、注册表）——那是调用方的语义
- 不做网络、不解析工具描述文本、不认识 LLM
